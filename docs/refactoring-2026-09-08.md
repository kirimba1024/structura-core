# Рефакторинг core: оценка и план

После этого этапа анализ и подготовка геометрии перенесены в
[structura-geo](https://github.com/kirimba1024/structura-geo). Ниже сохранены
результаты проверки до переноса; актуальные границы описаны в [архитектуре](architecture.md).

## Исходное состояние

На момент начала работы в core уже есть незакоммиченный рефакторинг: выделены
`structure`, `structure_writer`, `nbt_io`, этапы legacy-конвертации и сборка
отчёта. Эти изменения являются исходной точкой. Базовый прогон: 204 теста,
все проходят.

Размер не является критерием разделения сам по себе. Основные проблемы:

- `analyze.py` совмещает геометрические алгоритмы, кэши, классификацию и CLI.
  Поиск компонентов повторяется в анализаторе, комнатах и очистке. Плотные
  массивы зависят от расстояния между блоками, даже если блоков очень мало.
- `JavaWorld.read_region` смешивает выбор области, декодирование секций,
  объединение палитр, чтение сущностей и нормализацию координат.
- Парсеры форматов импортируют общие проверки чисел и векторов из внутренних
  функций `Structure`. Синтаксис состояний блоков тоже находится в модели,
  а операции замены материалов зависят от совместимого фасада `nbt`.
- Сдвиг блоков не обновляет координаты block entity внутри NBT. Чтение мира
  оставляет мировые координаты внутри NBT сущностей при локальных координатах
  внешних записей.

## Последовательность

1. Отделить синтаксис состояний и общую валидацию от модели документа.
   Сохранить публичные импорты и направление зависимостей.
2. Выделить общий поиск компонентов с ограниченной плотной памятью и обработкой
   разреженных координат. Разгрузить анализатор, сохранить метрики и отчёт.
3. Разделить чтение файлов региона, декодирование чанков и обработку сущностей.
   В `JavaWorld` оставить выбор области и координацию чтения.
4. Исправить подтверждённые ошибки координат и граничных параметров.
5. Проверить сохранение форматов и API, совместимость с render/edit, измерить
   расчёты до и после, обновить архитектурную документацию.

## Подход к тестам и объёму изменений

Существующие проверки сохранности NBT, атомарной записи, независимые форматные
фикстуры и проверки ошибочных входов полезны. Подмены файлового сбоя и парсера
проверяют гарантии атомарности и лимита чтения, поэтому сохраняются. Тест
битового потока использует независимое строковое представление битов и ловит
ошибки на границах слов; это не повод удалять его из-за частного импорта.

Новые тесты будут проверять наблюдаемые результаты, владение данными, границы
и сохранность файлов. Новые иерархии классов, mixin и общий движок всех форматов
не нужны: различия форматов существенны. Изменения производительности должны
подтверждаться измерениями; объяснения алгоритмов остаются в Markdown.

## Результат

План выполнен в core. Реализации получили самостоятельные обязанности,
публичные импорты и CLI сохранены. Новые модули описаны в
[архитектуре](architecture.md). Исходные тесты не удалялись.

| Перегруженный модуль | Строк до | Строк после |
|---|---:|---:|
| `analyze.py` | 490 | 284 |
| `world.py` | 218 | 102 |
| `structure.py` | 236 | 162 |
| `structure_writer.py` | 165 | 139 |
| `largest_component.py` | 142 | 110 |

Эти числа показывают разгрузку отдельных мест, а не сокращение всей библиотеки:
перенесённые реализации остаются в новых модулях. Дополнительный код нужен для
ограничения плотных массивов, обработки разреженных координат и проверок входа.
Сложные функции не заменены наследованием или цепочками посредников; циклов
между импортами верхнего уровня нет.

Подтверждённые исправления и улучшения:

- При сдвиге block entity получает координаты выходного блока. Уже пересчитанный
  вызывающим кодом NBT не сдвигается повторно. Неизменённые копии сохраняют NBT.
- Обычные сущности мира и подвесные сущности получают согласованные локальные
  координаты внутри и снаружи NBT. Сдвиг сохраняет собственное смещение якоря
  подвесной сущности относительно `blockPos`.
- Симметрия не зависит от дублирующихся индексов палитры, но различает свойства
  состояний. Для огромного разреженного размера не создаётся плотный state grid.
- Поиск компонентов/комнат использует одну реализацию с одинаковой связностью
  и выбором крупнейшего компонента при равенстве размеров. Полная сетка меток
  больше не остаётся в кэше анализатора.
- Профили этажности не выделяют массив через огромные пустые промежутки по Y.
  Гистограмма вычисляется один раз; возвращаемые коллекции не открывают кэши
  для изменения извне.
- Дублирующиеся секции/блоковые сущности мира, неверные лимиты, координаты,
  оси симметрии, ширина профиля и радиус освещения дают явные ошибки.
- Пустая геометрия больше не получает один фиктивный компонент мусора в
  эстетическом отчёте.
- Анализатор принимает готовый `Structure` и нативные пути, включая `Path`;
  JSON получает строковое имя источника. Нормализация Sponge/Bedrock сохраняет
  путь исходного документа. Возвращаемый счётчик `save_structure` правильно
  отражён в аннотации и проверке публичного API.

## Проверки

- 275 тестов core проходят как из исходников, так и с установленным wheel
  вне исходного пакета. Исходная база: 204 теста.
- Ruff и `git diff --check` проходят.
- Wheel и sdist собраны; Twine проверяет оба артефакта.
- Строгая проверка публичного API Pyright 1.1.411 против установленного wheel:
  0 ошибок, 0 предупреждений.
- Все 6 CLI entry point импортируются; JSON установленного `structura-analyze`
  проверен на структуре из 24 000 блоков.
- Во время проверки совместимости прошли 337 тестов render, 2 пропуска.
  Последующая работа ограничена core по уточнению пользователя. Изменения edit
  в этот рефакторинг не входят; совместимость с предварительным пересчётом
  координат проверяется регрессионным тестом core.

## Измерения

Python 3.9.6, NumPy 1.26.4, SciPy 1.13.1. Методика и воспроизводимый скрипт
описаны в [анализе](https://github.com/kirimba1024/structura-geo/blob/main/docs/analysis.md); исходные числа доступны в
[JSON](refactoring-2026-09-08.measurements.json). Измеряются расчёт отчёта без
чтения файла и отдельно пик выделений `tracemalloc`, не полный RSS процесса.

| Сценарий | Время до / после | Пик памяти до / после |
|---|---:|---:|
| 24 000 блоков, плотный объём | 156,6 / 156,2 мс | 5,60 / 5,31 МБ |
| 8 000 блоков, разреженное размещение | 56,5 / 55,2 мс | 6,28 / 3,25 МБ |

Отчёты обоих сценариев совпадают с исходной реализацией. Разницу времени не
следует трактовать как значимое ускорение. Во втором сценарии пик выделений
снизился примерно на 48%. Три блока с размером структуры до двух миллиардов
ячеек по X/Y обрабатываются за 0,135 мс при пике около 0,29 МБ; прежний
вариант на таком размере не запускался, чтобы не пытаться выделить весь объём.

## Сохранённые границы

Форматные кодеки не объединены в универсальный движок: их реальные различия
важнее внешнего сходства. Эвристики материалов и геометрии не переопределены;
их ограничения явно описаны. Входные атрибуты анализатора остаются снимком
для чтения: после редактирования нужен новый экземпляр. Полный GUI-прогон
и изменение edit относятся к отдельной работе.
